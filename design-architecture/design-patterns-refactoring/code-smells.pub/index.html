코드 스멜(code smell)은 즉시 드러나는 버그라기보다, 설계에 더 깊은 문제가 있을 가능성을 알려 주는 징후다. 스멜을 발견했다고 무조건 코드를 바꾸기보다 변경 비용이 실제로 커지고 있는지, 리팩터링으로 구조가 더 명확해지는지를 먼저 판단해야 한다.

중복과 크기에 관한 스멜

1. 중복 코드

같은 코드 구조가 둘 이상의 위치에 있다면 변경할 때마다 모든 복사본을 함께 수정해야 한다. 하나를 빠뜨리면 동작이 서로 달라진다.

개선 방향

  • 한 클래스의 여러 메서드에 같은 코드가 있으면 함수 추출(Extract Function)을 적용한다.
  • 형제 하위 클래스에 같은 코드가 있으면 함수를 추출한 뒤 메서드 올리기(Pull Up Method)를 적용한다.
  • 구조는 비슷하지만 일부 단계만 다르면 템플릿 메서드를 검토한다.
  • 목적은 같고 알고리즘만 다르면 더 단순한 알고리즘으로 통일하는 알고리즘 교체(Substitute Algorithm)를 검토한다.
  • 중복이 메서드의 가운데에 끼어 있다면 앞뒤 문맥을 포함한 주변 메서드 추출(Extract Surrounding Method)을 고려한다.
  • 관련 없는 클래스에 중복이 있다면 클래스 추출(Extract Class)이나 모듈 추출로 공통 책임을 옮긴다.

2. 장황한 메서드

긴 메서드는 여러 단계와 예외 상황을 한곳에 담아 의도를 파악하기 어렵게 한다. 짧은 메서드의 장점은 길이 자체보다 잘 지은 이름으로 세부 구현을 감출 수 있다는 점에 있다.

주석이 필요해 보이는 코드 덩어리는 별도 메서드로 추출하고, 수행 방식보다 목적이 드러나는 이름을 붙인다. 한 줄짜리 코드라도 중요한 개념을 표현한다면 추출할 가치가 있다.

개선 방향

  • 관련된 코드 덩어리에 함수 추출을 적용한다.
  • 임시 변수는 변수를 질의 함수로 바꾸기(Replace Temp with Query) 등으로 줄인다.
  • 긴 매개변수 목록은 매개변수 객체 도입(Introduce Parameter Object)이나 객체 통째로 넘기기(Preserve Whole Object)로 단순화한다.
  • 변수와 매개변수가 여전히 많으면 함수를 명령으로 바꾸기(Replace Function with Command)를 검토한다.
  • 복잡한 조건은 조건문 분해(Decompose Conditional)로 의도를 드러낸다.
  • 반복문 안의 서로 다른 작업을 별도 함수로 추출한다.

메서드를 지나치게 잘게 나누면 호출 흐름을 계속 오가야 하는 비용도 생긴다. 추출한 메서드의 이름만으로 상위 흐름을 읽을 수 있는지가 좋은 기준이다.

3. 방대한 클래스

필드와 메서드가 지나치게 많은 클래스는 여러 책임을 떠안고 있을 가능성이 크다. 함께 사용되는 필드 묶음과 특정 기능에만 관여하는 메서드를 찾으면 분리할 경계가 보인다.

개선 방향

  • 서로 연관된 필드와 메서드에 클래스 추출을 적용한다.
  • 특정 변형에만 필요한 책임은 하위 클래스 추출(Extract Subclass)을 고려한다.
  • 클래스 사용 방식이 클라이언트마다 다르면 역할별로 인터페이스 추출(Extract Interface)을 적용한다.
  • GUI 클래스에 도메인 데이터와 로직이 섞였다면 도메인 객체로 옮긴다. 화면 데이터와 도메인 데이터의 동기화가 필요하면 관측 데이터 복제(Duplicate Observed Data)를 활용할 수 있다.

4. 과다한 매개변수

매개변수 목록이 길면 호출 의도를 파악하기 어렵고, 새로운 데이터가 필요할 때마다 많은 호출부를 함께 수정해야 한다.

개선 방향

  • 객체가 이미 알고 있는 값이라면 별도 매개변수로 받지 말고 객체에 질의한다.
  • 한 객체에서 나온 여러 값은 객체 통째로 넘기기를 적용한다.
  • 늘 함께 전달되는 값은 매개변수 객체 도입으로 하나의 개념으로 묶는다.

호출되는 객체가 호출자에 의존해서는 안 되는 경계라면 개별 값을 전달하는 편이 더 나을 수 있다. 매개변수를 줄이려다 불필요한 결합을 만들지 않도록 주의한다.

변경에 관한 스멜

5. 수정의 산발

수정의 산발(Divergent Change)은 한 클래스가 서로 다른 이유로 여러 방식으로 자주 수정되는 상황이다. 예를 들어 데이터베이스 변경, 화면 표시 변경, 금융 상품 추가가 모두 같은 클래스를 건드린다면 책임이 섞여 있을 가능성이 크다.

개선 방향

특정 변경 이유에 함께 반응하는 필드와 메서드를 찾아 클래스 추출이나 모듈 추출로 묶는다. 목표는 한 클래스가 한 종류의 변경에 집중하게 만드는 것이다.

6. 기능의 산재

기능의 산재(Shotgun Surgery)는 하나의 변경을 완료하려고 여러 클래스의 작은 부분을 수정해야 하는 상황이다. 수정 위치를 찾기 어렵고 일부를 빠뜨릴 위험이 크다.

개선 방향

  • 함수 옮기기(Move Function)와 필드 옮기기(Move Field)로 함께 바뀌는 코드를 한 모듈에 모은다.
  • 적절한 기존 클래스가 없다면 새 클래스를 만든다.
  • 지나치게 잘게 분리된 클래스는 클래스 인라인(Inline Class)으로 합치는 것도 고려한다.

수정의 산발은 한 클래스에 여러 변경 이유가 있는 문제, 기능의 산재는 한 변경 이유가 여러 클래스에 흩어진 문제다. 둘 다 변경 이유와 모듈이 가능한 한 일대일로 대응하게 정리한다.

객체와 데이터 모델에 관한 스멜

7. 잘못된 소속

잘못된 소속(Feature Envy)은 메서드가 자신이 속한 클래스보다 다른 클래스의 데이터와 메서드를 더 많이 사용하는 상황이다.

개선 방향

  • 가장 많이 사용하는 데이터가 있는 클래스로 함수 옮기기를 적용한다.
  • 메서드의 일부만 소속이 잘못됐다면 먼저 함수 추출을 적용한 뒤 옮긴다.
  • 여러 클래스의 데이터를 사용한다면 코드를 역할별로 나눠 각각 적절한 위치로 이동한다.

전략, 방문자, 자기 위임처럼 의도적으로 데이터와 행동을 분리하는 패턴도 있다. 접근 횟수만 세지 말고 설계 의도를 함께 살핀다.

8. 데이터 뭉치

여러 필드나 매개변수가 항상 함께 나타난다면 독립된 개념을 이루고 있을 가능성이 크다. 그중 하나를 제거했을 때 나머지가 의미를 잃는지도 확인해 볼 수 있다.

개선 방향

  1. 함께 다니는 필드에 클래스 추출을 적용한다.
  2. 메서드 시그니처에는 매개변수 객체 도입이나 객체 통째로 넘기기를 적용한다.
  3. 새 객체의 데이터를 지나치게 사용하는 행동이 발견되면 그 행동도 새 객체로 옮긴다.

이 과정은 매개변수와 호출 코드를 줄일 뿐 아니라, 흩어져 있던 도메인 개념을 명시적인 객체로 만든다.

9. 강박적 기본 타입 사용

금액, 전화번호, 우편번호, 좌표처럼 규칙과 행동이 있는 값을 문자열이나 숫자로만 표현하면 검증과 변환 로직이 여러 곳에 흩어진다.

개선 방향

  • 의미가 있는 값은 기본형을 객체로 바꾸기(Replace Primitive with Object)를 적용한다.
  • 동작에 영향을 주는 타입 코드는 클래스나 상태·전략 패턴으로 바꾸는 것을 검토한다.
  • 함께 다니는 필드는 클래스 추출로 묶는다.
  • 기본 타입으로 된 매개변수 묶음에는 매개변수 객체 도입을 적용한다.
  • 배열의 각 위치가 별도 의미를 가진다면 배열을 객체로 바꾸기(Replace Array with Object)를 적용한다.

작은 값 객체는 타입 안정성을 높이고 검증 규칙을 한곳에 모을 수 있다.

조건과 상속에 관한 스멜

10. switch 문

타입에 따른 같은 switch 문이 여러 곳에서 반복되면 새 타입을 추가할 때 모든 분기를 찾아 수정해야 한다. 이런 경우 다형성으로 분산된 조건을 모을 수 있다.

개선 방향

  1. 조건문을 별도 함수로 추출한다.
  2. 타입 코드와 가장 가까운 클래스로 함수를 옮긴다.
  3. 타입 코드를 하위 클래스로 바꾸기 또는 조건부 로직을 다형성으로 바꾸기(Replace Conditional with Polymorphism)를 적용한다.

모든 switch 문이 문제인 것은 아니다. 분기가 적고 변경 가능성이 낮으며 한곳에만 존재한다면 다형성을 도입하는 편이 더 복잡할 수 있다. null 분기가 반복된다면 특이 케이스 추가(Introduce Special Case)나 널 객체 패턴을 검토한다.

11. 평행 상속 계층

한 상속 계층에 하위 클래스를 추가할 때마다 다른 계층에도 대응하는 하위 클래스를 만들어야 한다면 두 계층이 불필요하게 나뉘어 있을 수 있다. 두 계층의 클래스 이름이 비슷한 접두어나 접미어를 반복하는 것도 신호다.

개선 방향

한 계층의 인스턴스가 다른 계층의 인스턴스를 참조하도록 만들고, 함수 옮기기와 필드 옮기기를 적용해 중복된 계층을 제거한다.

불필요한 요소에 관한 스멜

12. 직무유기 클래스

클래스는 존재하는 것만으로도 이해와 유지보수 비용을 만든다. 리팩터링 후 책임이 거의 사라졌거나, 미래의 확장을 기대하며 만들었지만 사용되지 않는 클래스는 제거를 검토한다.

개선 방향

  • 역할이 거의 없는 하위 클래스는 계층 합치기(Collapse Hierarchy)를 적용한다.
  • 위임만 남은 작은 클래스는 클래스 인라인이나 모듈 인라인으로 합친다.

13. 막연한 범용 코드

언젠가 필요할 것이라는 가정으로 만든 추상 계층, 매개변수, 훅이 실제로 사용되지 않으면 현재의 코드를 이해하는 데 방해가 된다.

개선 방향

  • 기능이 없는 계층은 계층 합치기로 줄인다.
  • 불필요한 위임 클래스는 클래스 인라인을 적용한다.
  • 사용하지 않는 매개변수는 제거한다.
  • 실제 역할과 맞지 않는 메서드 이름은 변경한다.

프로덕션 코드에서는 쓰이지 않고 테스트만을 위해 존재하는 메서드도 의심해 볼 수 있다. 다만 테스트가 실제 기능을 지원하는 헬퍼와 픽스처는 유지해야 한다.

상태와 객체 탐색에 관한 스멜

14. 임시 필드

특정 상황이나 알고리즘을 실행할 때만 값이 채워지는 필드는 객체가 평소 어떤 상태여야 하는지 이해하기 어렵게 만든다.

개선 방향

  • 임시 필드와 관련 메서드를 클래스 추출로 별도 객체에 모은다.
  • 유효하지 않은 상태를 표현하는 조건이 반복되면 특이 케이스 추가나 널 객체 패턴을 적용한다.
  • 복잡한 알고리즘 때문에 매개변수를 필드에 저장했다면 알고리즘 전체를 별도의 메서드 객체로 추출한다.

15. 메시지 체인

a.getB().getC().getD()처럼 객체 내부를 따라가는 호출이 길어지면 클라이언트가 중간 객체의 관계에 결합된다. 관계 구조가 바뀔 때마다 호출부도 함께 바뀐다.

개선 방향

  • 위임 숨기기(Hide Delegate)로 중간 구조를 감춘다.
  • 최종 결과가 어디에 사용되는지 확인한 뒤, 그 로직을 함수로 추출하고 데이터에 더 가까운 객체로 옮긴다.
  • 여러 클라이언트가 같은 체인을 사용한다면 목적을 나타내는 메서드를 적절한 객체에 추가한다.

체인의 모든 단계를 무조건 감추면 단순 전달 메서드가 늘어나 과잉 중개 메서드 스멜로 이어질 수 있다.

위임과 결합에 관한 스멜

16. 과잉 중개 메서드

캡슐화를 위해 위임을 사용하지만, 클래스 인터페이스의 대부분이 다른 객체의 메서드를 그대로 호출한다면 중개 계층의 가치가 낮을 수 있다.

개선 방향

  • 중개자 제거(Remove Middle Man)로 실제 기능을 구현한 객체에 직접 접근하게 한다.
  • 별다른 역할이 없는 메서드는 함수 인라인(Inline Function)을 적용한다.
  • 중개 객체 자체가 실제 객체의 변형을 나타낸다면 위임을 상속으로 바꾸기(Replace Delegation with Inheritance)를 검토할 수 있다.

단, 중개 계층이 접근 제어, 트랜잭션, 로깅처럼 명확한 경계를 제공한다면 유지할 가치가 있다.

17. 지나친 관여

두 클래스가 서로의 비공개 데이터와 구현 세부 사항을 지나치게 많이 알면 독립적으로 변경하기 어렵다.

개선 방향

  • 함수 옮기기와 필드 옮기기로 각 클래스의 책임을 분명히 한다.
  • 양방향 연관을 단방향으로 바꿀 수 있는지 검토한다.
  • 두 클래스가 함께 필요로 하는 책임은 클래스 추출로 제3의 객체에 둔다.
  • 다른 객체의 세부 사항을 감추려면 위임 숨기기를 적용한다.
  • 상속 때문에 결합이 심하면 상속을 위임으로 바꾸기(Replace Inheritance with Delegation)를 검토한다.

인터페이스에 관한 스멜

18. 인터페이스가 다른 대용 클래스

두 클래스가 같은 역할을 수행하지만 메서드 이름이나 시그니처가 달라 서로 교체할 수 없는 상황이다.

개선 방향

  • 의미가 같은 메서드에는 함수 선언 바꾸기(Change Function Declaration)를 적용해 이름과 시그니처를 맞춘다.
  • 한쪽에 필요한 기능이 부족하다면 함수 옮기기로 프로토콜을 통일한다.
  • 공통 기능이 충분하다면 슈퍼클래스 추출(Extract Superclass)이나 공통 인터페이스 도입을 검토한다.

19. 미흡한 라이브러리 클래스

외부 라이브러리의 클래스를 직접 수정할 수 없는데 필요한 작은 기능이 빠져 있는 상황이다.

개선 방향

  • 필요한 함수가 적다면 클라이언트 쪽에 외부 클래스의 값을 받는 별도 함수를 만든다.
  • 추가 기능이 많다면 래퍼나 어댑터처럼 지역 확장(local extension) 역할을 하는 클래스를 만든다.

상속으로 확장할 수 있더라도 라이브러리의 내부 구현과 계약에 과도하게 결합되지 않는지 확인한다.

데이터와 상속에 관한 스멜

20. 데이터 클래스

데이터 클래스는 필드와 접근자만 제공하고, 데이터를 사용하는 행동은 모두 다른 클래스에 둔다. 그 결과 행동이 데이터가 있는 곳을 계속 탐색하게 된다.

개선 방향

  • 공개 필드는 캡슐화한다.
  • 컬렉션 필드는 내부 컬렉션이 그대로 노출되지 않도록 보호한다.
  • 변경할 필요가 없는 필드에서는 쓰기 메서드를 제거한다.
  • 데이터를 사용하는 로직에 함수 옮기기를 적용해 데이터 클래스 쪽으로 이동한다.
  • 전체를 옮길 수 없다면 먼저 옮길 수 있는 부분을 함수 추출한다.

DTO처럼 계층 사이에서 데이터를 전달하는 것이 명확한 역할인 클래스는 행동이 없어도 문제가 아닐 수 있다.

21. 방치된 상속물

하위 클래스가 상위 클래스에서 물려받은 메서드나 데이터를 대부분 사용하지 않거나, 상위 타입의 인터페이스를 제대로 지원하지 못하면 상속 관계가 잘못됐을 가능성이 있다.

개선 방향

  • 일부 하위 클래스만 사용하는 기능은 메서드 내리기(Push Down Method)와 필드 내리기(Push Down Field)로 적절한 계층에 둔다.
  • 하위 클래스가 구현은 재사용하지만 상위 타입의 계약을 따를 수 없다면 상속을 위임으로 바꾸기를 적용한다.

단순히 일부 구현을 사용하지 않는 것보다 상위 타입의 인터페이스를 거부하는 상황이 더 심각하다. 이는 리스코프 치환 원칙을 위반할 수 있다.

설명에 관한 스멜

22. 불필요한 주석

주석 자체가 문제인 것은 아니다. 복잡한 코드의 의도를 설명하는 대신 나쁜 구조를 가리는 탈취제처럼 사용되는 주석이 문제다.

개선 방향

  • 코드 구간의 기능을 설명하는 주석은 함수 추출과 명확한 이름으로 대체할 수 있는지 확인한다.
  • 이미 함수로 나뉘었는데도 설명이 필요하다면 이름을 개선한다.
  • 시스템이 반드시 만족해야 할 조건은 어서션 추가(Introduce Assertion)로 명시한다.

다음과 같은 주석은 여전히 가치가 있다.

  • 왜 이 구현을 선택했는지 설명하는 주석
  • 불확실하거나 추가 확인이 필요한 부분
  • 외부 제약이나 쉽게 잊을 수 있는 주의 사항
  • 코드만으로 드러나지 않는 의사결정의 맥락

리팩터링을 시작하는 기준

코드 스멜은 자동으로 수정해야 하는 오류 목록이 아니다. 다음 질문을 통해 우선순위를 정한다.

  1. 이 구조 때문에 최근 변경이 실제로 어려웠는가?
  2. 같은 종류의 수정이 앞으로도 반복될 가능성이 높은가?
  3. 문제를 설명하는 테스트가 있어 안전하게 바꿀 수 있는가?
  4. 리팩터링 후 책임과 의도가 더 명확해지는가?
  5. 새 추상화가 해결하는 문제보다 더 큰 복잡도를 만들지는 않는가?

작은 단계로 구조를 개선하고 매 단계마다 테스트를 실행하면, 동작을 보존하면서 코드의 설계를 점진적으로 다듬을 수 있다.
