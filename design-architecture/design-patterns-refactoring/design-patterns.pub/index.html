디자인 패턴 핵심 정리

주요 객체지향 디자인 패턴의 목적과 구조, 서로 비슷한 패턴의 차이, 적용 시 주의점을 유형별로 정리합니다.

디자인 패턴은 반복해서 등장하는 설계 문제에 이름을 붙이고, 검증된 해결 구조를 공유하는 방법이다. 패턴의 형태보다 어떤 문제를 해결하는지, 무엇을 교환하거나 분리하는지, 그 대가로 복잡도가 얼마나 늘어나는지를 이해하는 것이 중요하다.

패턴을 이해하기 위한 객체지향 원칙

  • 바뀌는 부분은 캡슐화한다.
  • 구현이 아닌 인터페이스에 맞춰 프로그래밍한다.
  • 상속보다 구성을 활용한다.
  • 상호작용하는 객체 사이의 결합을 느슨하게 유지한다.

행동 패턴

전략 패턴

전략 패턴(Strategy Pattern)은 알고리즘군을 정의하고 각각을 캡슐화하여 교체할 수 있게 한다. 알고리즘을 사용하는 클라이언트와 실제 구현이 분리되므로 실행 중에도 행동을 바꿀 수 있다.

예를 들어 Duck이 비행 행동을 직접 구현하는 대신 FlyBehavior 인터페이스를 구성 요소로 가지면, 오리의 종류와 관계없이 비행 알고리즘을 교체할 수 있다.

옵저버 패턴

옵저버 패턴(Observer Pattern)은 한 객체의 상태가 바뀌었을 때 그 객체에 의존하는 여러 객체에 변화를 알리는 일대다 의존 관계를 정의한다.

주제(subject)는 옵저버의 구체적인 구현을 몰라도 된다. 새 옵저버를 등록하거나 기존 옵저버를 제거해도 주제의 핵심 로직은 바뀌지 않는다.

커맨드 패턴

커맨드 패턴(Command Pattern)은 요청을 객체로 캡슐화한다. 호출자는 수신자(receiver)가 요청을 어떻게 처리하는지 몰라도 되며, 커맨드를 매개변수처럼 전달할 수 있다.

다음과 같은 기능을 구현할 때 유용하다.

  • 요청을 큐에 저장하거나 지연 실행하기
  • 요청 이력을 로그로 남기기
  • 실행 취소(undo) 지원하기
  • 여러 요청을 하나의 트랜잭션처럼 구성하기

일반적인 커맨드는 요청을 수신자에게 전달하지만, 요청을 스스로 처리하는 이른바 스마트 커맨드를 사용할 수도 있다.

템플릿 메서드 패턴

템플릿 메서드 패턴(Template Method Pattern)은 상위 클래스의 메서드에서 알고리즘의 골격을 정의하고, 일부 단계를 하위 클래스가 구현하거나 재정의하게 한다. 알고리즘의 전체 순서는 유지하면서 특정 단계만 바꿀 수 있다.

추상 메서드와 훅

  • 하위 클래스가 반드시 구현해야 하는 단계에는 추상 메서드를 사용한다.
  • 선택적으로 확장할 수 있는 단계에는 기본 구현이 있거나 본문이 비어 있는 훅(hook)을 사용한다.

훅은 알고리즘의 특정 단계 전후에 하위 클래스가 반응할 기회를 제공할 때도 유용하다.

비슷한 패턴과의 차이

패턴변화를 만드는 방법
템플릿 메서드상속을 사용해 알고리즘의 일부 단계를 하위 클래스가 구현한다.
전략구성을 사용해 교체 가능한 알고리즘 전체를 캡슐화한다.
팩토리 메서드생성할 구체 클래스를 하위 클래스가 결정한다.

이터레이터 패턴

이터레이터 패턴(Iterator Pattern)은 컬렉션의 내부 표현을 노출하지 않고 모든 항목에 순차적으로 접근하는 방법을 제공한다. 컬렉션은 객체 관리에 집중하고, 순회 책임은 이터레이터가 맡는다.

상태 패턴

상태 패턴(State Pattern)은 객체의 내부 상태를 별도의 클래스로 캡슐화하고, 현재 상태 객체에 행동을 위임한다. 상태 객체가 바뀌면 컨텍스트의 행동도 자연스럽게 바뀐다.

상태 전환 규칙이 고정되어 있다면 컨텍스트가 흐름을 관리할 수 있다. 전환이 상태마다 동적으로 결정된다면 각 상태 클래스가 다음 상태를 결정하게 할 수 있다. 클라이언트는 상태 객체를 직접 조작하지 않고 컨텍스트를 통해 요청한다.

상태와 전략 비교

구분상태 패턴전략 패턴
목적내부 상태에 따라 행동을 바꾼다.필요에 따라 알고리즘을 교체한다.
선택 주체컨텍스트나 현재 상태가 다음 상태를 결정한다.주로 클라이언트가 전략을 선택한다.
클라이언트의 인식상태 객체를 거의 알지 못한다.어떤 전략을 사용할지 아는 경우가 많다.
대표 대안복잡한 상태 조건문행동별 하위 클래스

상태 클래스를 추가하면 객체 수가 늘어나지만, 거대한 조건문을 여러 개의 명확한 상태 객체로 분리할 수 있다.

생성 패턴

팩토리 패턴

팩토리 계열 패턴은 객체 생성을 캡슐화하여 클라이언트와 구체 제품 사이의 결합을 줄인다.

팩토리 메서드와 추상 팩토리

구분팩토리 메서드추상 팩토리
생성 방식상속을 사용한다.객체 구성을 사용한다.
결정 주체하위 클래스가 생성할 구체 제품을 결정한다.팩토리 구현이 관련 제품군을 생성한다.
적합한 상황필요한 구체 클래스를 미리 알 수 없거나 생성을 확장해야 할 때서로 관련된 여러 제품을 일관된 조합으로 만들어야 할 때

두 패턴 모두 클라이언트가 실제 구체 제품을 직접 생성하지 않게 하여 특정 구현에 대한 의존을 줄인다.

싱글턴 패턴

싱글턴 패턴(Singleton Pattern)은 클래스의 인스턴스를 하나로 제한하고 어디서든 같은 인스턴스에 접근할 수 있게 한다. 스레드 풀, 캐시, 설정, 로그처럼 하나의 공유 인스턴스가 필요한 대상에 사용되곤 한다.

전역 변수와 달리 객체 생성을 실제로 필요할 때까지 미룰 수 있고, 접근 방식을 클래스 안에서 제어할 수 있다. 하지만 다음 사항을 주의해야 한다.

  • 전역 상태처럼 사용하면 의존성이 숨고 테스트가 어려워진다.
  • 동시성 환경에서는 안전한 초기화가 필요하다.
  • 클래스 로더가 여러 개라면 클래스 로더마다 인스턴스가 생길 수 있다.

구조 패턴

데코레이터 패턴

데코레이터 패턴(Decorator Pattern)은 객체를 같은 인터페이스의 다른 객체로 감싸 새로운 행동을 동적으로 추가한다. 하위 클래스를 계속 만드는 방식보다 기능을 유연하게 조합할 수 있다.

  • 구성과 위임으로 실행 중에 책임을 추가한다.
  • 데코레이터는 감싸는 구성 요소와 같은 타입을 따른다.
  • 여러 데코레이터를 겹쳐 사용할 수 있다.
  • 클라이언트는 보통 데코레이터의 존재를 알 필요가 없다.

다만 클라이언트가 구체 타입에 의존하면 적용하기 어렵다. 작은 객체가 많이 생기고 데코레이터의 조합을 추적하기 어려워질 수도 있다.

어댑터 패턴

어댑터 패턴(Adapter Pattern)은 기존 클래스의 인터페이스를 클라이언트가 기대하는 다른 인터페이스로 변환한다.

  1. 클라이언트가 타깃(target) 인터페이스로 어댑터를 호출한다.
  2. 어댑터가 요청을 어댑티(adaptee)의 하나 이상의 메서드 호출로 변환한다.
  3. 어댑티의 결과가 어댑터를 거쳐 클라이언트에 반환된다.

하나의 어댑터가 타깃 인터페이스를 구현하기 위해 여러 어댑티를 함께 사용할 수도 있다. 타깃 인터페이스가 크면 구현 비용도 커지므로, 전체를 변환하는 것이 정말 필요한지 검토해야 한다.

클래스 어댑터는 구성을 사용하는 객체 어댑터와 달리 상속으로 타깃과 어댑티를 연결한다. 언어에 따라 다중 상속이 필요할 수 있다.

퍼사드 패턴

퍼사드 패턴(Facade Pattern)은 복잡한 서브시스템을 단순하게 사용할 수 있는 통합 인터페이스를 제공한다. 인터페이스를 간소화할 뿐 아니라 클라이언트와 서브시스템의 구체 구성 요소를 분리한다.

퍼사드를 제공해도 필요하다면 클라이언트가 서브시스템의 개별 기능에 직접 접근할 수 있다.

데코레이터, 어댑터, 퍼사드 비교

패턴객체를 감싸는 목적
데코레이터행동을 추가한다.
어댑터인터페이스를 변환한다.
퍼사드여러 객체로 구성된 서브시스템을 단순화한다.

컴포지트 패턴

컴포지트 패턴(Composite Pattern)은 객체를 트리 구조로 구성하여 부분–전체 계층을 표현한다. 클라이언트는 잎(leaf) 객체와 자식을 가진 복합(composite) 객체를 같은 인터페이스로 다룬다.

복합 객체의 자식은 다시 복합 객체이거나 잎일 수 있다. 이 재귀적인 구조 덕분에 클라이언트는 개별 객체인지 객체 묶음인지 구분하지 않고 전체 구조에 같은 작업을 적용할 수 있다.

투명성과 안전성

구성 요소 인터페이스에 자식 관리 기능과 잎의 기능을 모두 넣으면 클라이언트는 두 종류를 투명하게 다룰 수 있다. 반면 잎 객체에도 의미 없는 자식 관리 메서드가 노출되므로 타입 안전성이 떨어질 수 있다. 인터페이스를 단순화하는 이점과 잘못된 호출 가능성 사이의 균형이 필요하다.

프록시 패턴

프록시 패턴(Proxy Pattern)은 다른 객체를 대신하는 객체를 제공해 접근을 제어한다.

  • 원격 프록시: 다른 프로세스나 네트워크에 있는 객체를 로컬 객체처럼 사용하게 한다.
  • 가상 프록시: 생성 비용이 큰 객체가 실제로 필요할 때까지 생성을 미룬다.
  • 보호 프록시: 호출자의 권한에 따라 메서드 접근을 제한한다.

동적 프록시를 지원하는 언어와 런타임에서는 호출 처리기를 통해 프록시 클래스를 실행 중에 만들 수도 있다. 다른 래퍼 패턴과 마찬가지로 클래스와 객체 수가 늘어난다는 비용이 있다.

패턴주된 목적
데코레이터객체에 행동을 추가한다.
프록시객체에 대한 접근을 제어한다.

컴파운드 패턴과 MVC

컴파운드 패턴(compound pattern)은 여러 패턴을 함께 사용해 더 큰 설계 문제를 해결한다. MVC(Model–View–Controller)는 대표적인 예다.

구성 요소의 역할

  • 모델: 데이터, 상태, 비즈니스 로직을 관리한다. 상태가 바뀌면 옵저버에 알릴 수 있지만 뷰와 컨트롤러의 구체 구현에는 관심을 두지 않는다.
  • 뷰: 모델을 표현한다. 화면에 필요한 상태와 데이터를 모델에서 읽는다.
  • 컨트롤러: 사용자 입력을 해석하고 모델에 어떤 작업을 요청할지 결정한다.

일반적인 상호작용

  1. 사용자가 뷰를 통해 입력한다.
  2. 컨트롤러가 입력을 해석하고 모델에 상태 변경을 요청한다.
  3. 필요하면 컨트롤러가 뷰 변경을 요청한다.
  4. 모델의 상태가 바뀌면 모델이 뷰에 알린다.
  5. 뷰가 모델에서 최신 상태를 읽어 화면을 갱신한다.

컨트롤러도 모델의 옵저버가 되어 상태 변화를 전달받을 수 있다. 컨트롤러를 별도로 두면 입력 해석과 제어 로직이 뷰에서 분리되어, 뷰를 다른 모델에 연결하거나 인터페이스를 교체하기 쉬워진다.

디자인 패턴의 정의와 분류

패턴은 특정 컨텍스트에서 반복해서 발생하는 문제에 대한 재사용 가능한 설계 해결책이다.

  • 컨텍스트: 패턴이 적용되는 반복 가능한 상황
  • 문제: 그 상황에서 달성하려는 목적과 제약 조건
  • 해결책: 제약 안에서 목적을 달성하게 하는 일반적인 설계 구조

GoF 디자인 패턴은 보통 다음 세 유형으로 분류한다.

분류목적대표 패턴
생성객체 생성 과정과 구체 타입을 분리한다.추상 팩토리, 팩토리 메서드, 싱글턴, 빌더, 프로토타입
구조클래스와 객체를 조합해 더 큰 구조를 만든다.어댑터, 브리지, 컴포지트, 데코레이터, 퍼사드, 플라이웨이트, 프록시
행동객체의 역할 분담과 상호작용 방식을 정의한다.책임 연쇄, 커맨드, 인터프리터, 이터레이터, 중재자, 메멘토, 옵저버, 상태, 전략, 템플릿 메서드, 방문자

패턴을 적용하기 전에

  • 패턴을 억지로 적용하지 말고 현재 조건을 만족하는 가장 단순한 해결책부터 선택한다.
  • 필요하지 않은 패턴은 객체와 간접 계층만 늘려 시스템을 복잡하게 만든다.
  • 패턴을 적용한 뒤 기대했던 유연성이 생기지 않고 복잡도만 늘었다면 제거를 검토한다.
  • 패턴의 예제 구조를 그대로 복제하기보다 문제와 제약에 맞게 조정한다.
  • 이름보다 의도와 트레이드오프를 이해한다.
