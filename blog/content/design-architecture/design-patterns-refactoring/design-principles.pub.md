디자인 원칙은 특정 패턴을 외우기 위한 규칙이 아니라, 변경하기 쉽고 이해하기 쉬운 구조를 판단하는 기준이다. 이 글에서는 여러 디자인 패턴의 바탕이 되는 객체지향 원칙과 적용할 때의 주의점을 정리한다.

## 한눈에 보는 핵심 원칙

| 원칙 | 핵심 질문 | 관련 패턴 |
| --- | --- | --- |
| 변화의 캡슐화 | 무엇이 자주 바뀌는가? | 전략 패턴 |
| 인터페이스에 맞춘 프로그래밍 | 클라이언트가 구체 구현을 알아야 하는가? | 전략 패턴, 팩토리 패턴 |
| 상속보다 구성 | 실행 중에 행동을 교체해야 하는가? | 전략 패턴, 데코레이터 패턴 |
| 느슨한 결합 | 한 객체의 변경이 다른 객체로 얼마나 퍼지는가? | 옵저버 패턴 |
| 개방–폐쇄 원칙 | 기존 코드를 수정하지 않고 확장할 수 있는가? | 데코레이터 패턴 |
| 의존성 역전 원칙 | 고수준 정책이 저수준 구현에 묶여 있는가? | 팩토리 패턴 |
| 최소 지식 원칙 | 객체가 너무 많은 협력자의 내부를 알고 있는가? | 퍼사드 패턴 |
| 할리우드 원칙 | 전체 흐름을 누가 제어하는가? | 템플릿 메서드 패턴 |
| 단일 책임 원칙 | 이 클래스를 바꾸는 이유가 둘 이상인가? | 여러 패턴의 공통 기반 |

## 변하는 부분을 분리하고 캡슐화한다

애플리케이션에서 달라지는 부분을 찾아 안정적인 부분과 분리한다. 바뀌는 부분을 별도로 캡슐화하면 나머지 코드를 건드리지 않고 그 부분만 수정하거나 확장할 수 있다.

- 변경의 영향을 좁힌다.
- 의도하지 않은 회귀를 줄인다.
- 실행 중에 행동을 교체할 수 있는 구조를 만들 수 있다.

전략 패턴은 변하는 알고리즘을 각각 캡슐화하고 교체 가능하게 만드는 대표적인 예다.

## 구현이 아닌 인터페이스에 맞춰 프로그래밍한다

변수의 선언 타입과 객체 간의 계약을 상위 타입이나 인터페이스로 표현한다. 클라이언트가 구체 클래스에 묶이지 않으면 실행 시점에 다른 구현을 선택할 수 있고, 아직 존재하지 않는 구현도 같은 계약 아래 추가할 수 있다.

이 원칙은 단순히 모든 곳에 인터페이스를 만들라는 뜻이 아니다. 교체 가능성이 있거나 여러 구현을 같은 방식으로 다뤄야 하는 경계에서 효과가 크다.

## 상속보다 구성을 활용한다

상속은 컴파일 시점에 관계가 고정되고 상위 클래스의 구현 세부 사항에 결합되기 쉽다. 구성(composition)은 필요한 행동을 다른 객체에 맡기므로 실행 중에 구현을 교체하기 쉽고, 독립적으로 변화하는 기능을 조합할 수 있다.

전략 패턴과 데코레이터 패턴은 구성을 통해 행동을 선택하거나 덧붙이는 대표적인 사례다.

## 상호작용하는 객체를 느슨하게 결합한다

느슨한 결합은 객체가 협력자의 구체적인 구현을 최소한으로 알도록 설계하는 것이다. 한 객체가 바뀌어도 다른 객체가 함께 수정될 가능성이 줄어든다.

옵저버 패턴에서는 주제(subject)가 옵저버의 구체 클래스 대신 공통 인터페이스에 의존한다. 이 덕분에 주제의 코드를 바꾸지 않고 옵저버를 추가하거나 제거할 수 있다.

## 개방–폐쇄 원칙

**개방–폐쇄 원칙(Open–Closed Principle, OCP)**은 소프트웨어 구성 요소가 확장에는 열려 있고 수정에는 닫혀 있어야 한다는 원칙이다.

기존 코드를 직접 수정하는 대신 새로운 구현을 추가해 행동을 확장할 수 있다면 변경에 따른 위험이 줄어든다. 데코레이터 패턴은 기존 객체를 수정하지 않고 책임을 동적으로 추가한다.

> 모든 변경 가능성을 미리 추상화하면 오히려 설계가 복잡해진다. 실제로 반복되는 변화 축을 발견했을 때 적용하는 편이 안전하다.

## 의존성 역전 원칙

**의존성 역전 원칙(Dependency Inversion Principle, DIP)**은 고수준 정책과 저수준 구현 모두 구체 클래스가 아니라 추상화에 의존해야 한다는 원칙이다.

실무에서는 다음 질문으로 점검할 수 있다.

- 객체를 생성하는 코드가 구체 클래스 전반에 흩어져 있지 않은가?
- 상속이 단지 기존 구현을 재사용하기 위한 수단으로 쓰이지 않았는가?
- 상위 타입의 메서드를 자주 재정의해야 할 만큼 추상화가 불안정하지 않은가?

팩토리 패턴은 객체 생성 책임을 분리하여 클라이언트가 구체 클래스에 직접 의존하는 상황을 줄인다.

## 최소 지식 원칙

**최소 지식 원칙(Principle of Least Knowledge)** 또는 **데메테르의 법칙(Law of Demeter)**은 객체가 가까운 협력자하고만 상호작용하도록 제한한다.

일반적으로 메서드 안에서는 다음 객체의 메서드만 호출하는 것이 좋다.

1. 객체 자신
2. 매개변수로 전달받은 객체
3. 메서드 안에서 생성한 객체
4. 객체가 직접 소유한 구성 요소

다른 객체의 내부 구성 요소를 연속해서 탐색하면 클라이언트가 내부 구조에 결합된다.

```java
// 최소 지식 원칙을 따르지 않은 경우
public float getTemperature() {
    Thermometer thermometer = station.getThermometer();
    return thermometer.getTemperature();
}

// Station이 내부 협력자에게 요청을 위임한다.
public float getTemperature() {
    return station.getTemperature();
}
```

두 번째 방식에서는 클라이언트가 `Station` 내부에 `Thermometer`가 있다는 사실을 알 필요가 없다. 내부 구조가 바뀌어도 클라이언트는 영향을 덜 받는다.

### 허용되는 협력의 예

```java
public class Car {
    private final Engine engine;

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void start(Key key) {
        Doors doors = new Doors();
        boolean authorized = key.turns(); // 매개변수

        if (authorized) {
            engine.start();                // 직접 소유한 구성 요소
            updateDashboardDisplay();      // 객체 자신의 메서드
            doors.lock();                  // 메서드 안에서 생성한 객체
        }
    }

    private void updateDashboardDisplay() {
        // 디스플레이 갱신
    }
}
```

최소 지식 원칙을 지나치게 적용하면 단순 위임만 하는 래퍼 메서드가 늘어날 수 있다. 의존성 감소와 추가되는 간접 계층의 비용을 함께 판단해야 한다.

## 할리우드 원칙

> 먼저 연락하지 마세요. 저희가 연락드리겠습니다.

**할리우드 원칙(Hollywood Principle)**은 저수준 구성 요소가 고수준 구성 요소를 직접 제어하지 않고, 고수준 구성 요소가 필요한 시점에 저수준 구성 요소를 호출하도록 한다.

템플릿 메서드 패턴에서는 상위 클래스가 알고리즘의 전체 흐름을 제어하고, 하위 클래스는 정해진 확장 지점에서 일부 단계만 구현한다. 이를 통해 고수준과 저수준 구성 요소가 서로 복잡하게 의존하는 **의존성 부패(dependency rot)**를 줄일 수 있다.

## 단일 책임 원칙

**단일 책임 원칙(Single Responsibility Principle, SRP)**은 클래스를 변경하는 이유가 하나뿐이어야 한다는 원칙이다.

클래스가 여러 역할을 담당하면 역할마다 새로운 변경 이유가 생긴다. 서로 다른 시점과 이유로 바뀌는 책임은 별도의 클래스로 분리하는 편이 낫다.

### 응집도

응집도(cohesion)는 클래스나 모듈이 하나의 목적을 얼마나 일관되게 지원하는지를 나타낸다. 높은 응집도는 단일 책임을 판단하는 유용한 신호다. 메서드와 필드가 하나의 목적을 중심으로 밀접하게 연결되어 있다면 책임도 비교적 분명하다.

## 적용할 때 기억할 점

- 원칙은 설계를 판단하는 기준이지 기계적으로 지켜야 할 체크리스트가 아니다.
- 아직 존재하지 않는 변화까지 모두 추상화하지 않는다.
- 결합을 줄이기 위해 추가한 간접 계층이 이해 비용을 높이지 않는지 확인한다.
- 패턴보다 먼저 책임, 변화의 방향, 객체 사이의 계약을 살핀다.
