## 출발점: 검색 공간을 줄여야 한다

큰 테이블에서 특정 행을 찾는 가장 단순한 방법은 **Full Table Scan**이다. 힙(heap)의
모든 페이지를 처음부터 끝까지 읽으면 언젠가는 원하는 행을 만난다. 문제는 비용이다.

행 하나가 128바이트이고 행이 10억 개, 페이지 크기가 8KB라고 하자.

```text
페이지당 행 수 = 8,192 / 128 ≈ 64행
전체 페이지 수 = 1,000,000,000 / 64 ≈ 15,625,000 페이지
전체 크기      ≈ 15,625,000 × 8KB ≈ 122GB
```

`WHERE id = 999991931` 하나를 찾기 위해 최악의 경우 **1,500만 번 이상의 페이지 읽기**가
필요하다. 순차 읽기라 랜덤 읽기보다는 빠르지만, 초당 1GB를 읽는 스토리지에서도 2분이
넘는다. 트랜잭션 하나에 쓸 수 있는 시간이 아니다.

| ID | Name |
|----|------|
| 1 | John |
| 2 | Ali |
| ... | ... |
| 591828736 | Chip |
| ... | ... |
| 999991931 | Kory |

`ID = 5`는 첫 페이지에서 바로 찾을 수 있지만 `ID = 999991931`은 사실상 전부를 읽어야
한다. 그래서 필요한 것이 **검색 공간(search space)을 줄여 주는 별도의 자료구조**,
즉 인덱스다.

## 왜 이진 탐색 트리로는 안 되는가

정렬된 데이터에서의 검색이라면 이진 탐색 트리(BST)나 AVL 트리, 레드-블랙 트리를
떠올리는 게 자연스럽다. 실제로 시간 복잡도는 모두 `O(log N)`이다. 그런데도 디스크
기반 데이터베이스는 이들을 인덱스로 쓰지 않는다. 이유는 **복잡도의 밑(base)이 다르기
때문**이다.

메모리 자료구조의 비용 모델은 "비교 연산 횟수"다. 디스크 자료구조의 비용 모델은
**"디스크 페이지를 몇 번 읽는가"** 다. 이 둘은 자릿수가 다르다.

| 접근 | 대략적인 지연 시간 | 비율 |
|------|-----------------|------|
| L1 캐시 참조 | ~1ns | 1 |
| 메인 메모리 참조 | ~100ns | 100 |
| NVMe SSD 랜덤 읽기 | ~100μs | 100,000 |
| HDD 랜덤 읽기 (seek 포함) | ~10ms | 10,000,000 |

이진 트리는 노드 하나에 **키 하나**만 담는다. 노드마다 자식이 둘뿐이므로 10억 개
항목에 대한 트리 높이는 `log₂(10⁹) ≈ 30`이다. 각 노드가 디스크의 서로 다른 위치에
흩어져 있으므로, 검색 한 번에 **약 30번의 랜덤 IO**가 발생한다. SSD에서도 3ms,
HDD라면 300ms다.

게다가 디스크는 바이트 단위로 읽을 수 없다. 최소 단위가 페이지(Postgres 8KB,
MySQL InnoDB 16KB)다. 16바이트짜리 이진 트리 노드 하나를 읽으려고 8KB를 읽어 오면
**나머지 8,176바이트를 버리는 셈**이다.

여기서 결론이 나온다.

> 디스크 자료구조는 **높이를 줄이고**, **한 번 읽은 페이지를 최대한 활용**해야 한다.
> 그러려면 노드 하나에 키를 최대한 많이 담아야 한다.

이것이 B-Tree의 설계 동기다. **1 노드 = 1 디스크 페이지**로 맞추고, 그 페이지 안에
수백 개의 키를 담아 자식을 수백 개로 분기시킨다. 밑이 2인 로그를 밑이 수백인 로그로
바꾸는 것이다.

```text
이진 트리   : log₂(10억)   ≈ 30 레벨  → 랜덤 IO 30회
B-Tree(400) : log₄₀₀(10억) ≈ 3.5 레벨 → 랜덤 IO 4회
```

## B-Tree의 구조

### 정의와 불변식

차수(order/degree)가 `m`인 B-Tree는 다음을 만족한다.

- 모든 노드는 최대 `m`개의 자식과 최대 `m-1`개의 키를 가진다
- 루트를 제외한 모든 노드는 최소 `⌈m/2⌉ - 1`개의 키를 가진다 (최소 채움률 약 50%)
- 노드 안의 키는 정렬되어 있고, 키 사이사이에 자식 포인터가 놓인다
- **모든 리프 노드는 같은 깊이에 있다** (완전 균형)

마지막 조건이 핵심이다. B-Tree는 삽입/삭제 시 회전(rotation)이 아니라
**분할(split)과 병합(merge)** 으로 균형을 유지하며, 트리가 위로 자란다.
따라서 어떤 키를 찾든 **IO 횟수가 항상 트리 높이와 같다**. 최악과 평균이 같다는 점은
응답 시간 예측이 중요한 OLTP에서 큰 장점이다.

### 노드의 내용

B-Tree에서는 **모든 노드(루트, 내부, 리프)의 모든 엔트리가 key와 value를 함께 가진다.**
여기서 value는 보통 실제 행을 가리키는 **데이터 포인터**다.

- PostgreSQL: TID(tuple id) — `(페이지 번호, 페이지 내 오프셋)`, 6바이트
- MySQL InnoDB: Primary Key 값

```text
         [2:702 | 4:704]          ← Root Node
        /       |       \
  [1:701]   [3:703]   [5:705]     ← Leaf Nodes
```

`5:705`에서 `5`는 키, `705`는 그 행이 저장된 위치를 가리키는 포인터다.

### 검색 과정

**`ID = 3` 찾기**

1. 루트 페이지를 읽는다 (IO 1) → `2`, `4` 확인
2. `2 < 3 < 4` 이므로 가운데 자식으로 이동
3. 리프 페이지를 읽는다 (IO 2) → `3:703` 발견
4. TID `703`으로 힙 페이지를 읽는다 (IO 3) → 실제 행 획득

노드 안에서 키를 찾는 것은 이미 메모리에 올라온 페이지 안에서의 이진 탐색이므로
사실상 공짜다. **비용은 오직 페이지를 몇 개 읽었는가로 결정된다.**

항목이 11개로 늘어난 B-Tree는 이렇게 자란다.

```text
              [4:704 | 8:802]              ← Root
             /       |       \
      [2:702]    [6:800]    [10:804]       ← Internal
       /   \      /   \       /    \
 [1:701][3:703][5:705][7:801][9:803][11:805] ← Leaf
```

> B-Tree 시각화 도구: <https://www.cs.usfca.edu/~galles/visualization/BTree.html>

### 삽입과 분할

키를 넣을 리프에 자리가 없으면 **노드를 반으로 쪼개고(split), 가운데 키를 부모로
올린다.** 부모도 가득 차 있으면 부모를 다시 쪼갠다. 이 연쇄가 루트까지 도달하면
루트가 분할되고 **트리의 높이가 1 증가한다.** B-Tree가 아래가 아니라 위로 자라는
이유이자, 모든 리프의 깊이가 항상 같은 이유다.

삭제는 반대다. 노드의 채움률이 최소치 아래로 떨어지면 형제에게서 키를 빌리거나
(borrow/redistribute) 형제와 병합(merge)한다.

## fanout: 이 모든 것을 결정하는 숫자

트리의 높이는 **fanout(노드 하나가 가지는 자식 수)** 이 결정한다. 그리고 fanout은
`페이지 크기 ÷ 엔트리 크기`다. **엔트리를 작게 만들수록 트리가 낮아지고 IO가 줄어든다.**

PostgreSQL의 8KB 페이지에 `BIGINT` 키를 인덱싱한다고 하자.

```text
인덱스 엔트리 = IndexTuple 헤더 8B + 키 8B = 16B
              + 페이지 내 라인 포인터 4B
              ≈ 20B

fanout ≈ 8,192 × 0.9 (fillfactor) / 20 ≈ 약 370
```

이 fanout으로 담을 수 있는 행 수는 다음과 같다.

| 트리 높이 | 리프 페이지 수 | 담을 수 있는 행 수 | 검색 IO |
|-----------|---------------|------------------|---------|
| 2 | 370 | 약 13만 | 2 |
| 3 | 137,000 | 약 5,000만 | 3 |
| 4 | 5,000만 | 약 180억 | 4 |

**10억 행 테이블의 인덱스 높이가 4를 넘기 어렵다**는 뜻이다. 그리고 상위 레벨은
접근 빈도가 압도적으로 높아 버퍼 풀에 상주하므로, 실제 디스크 IO는 리프 1회 +
힙 1회 수준으로 떨어진다.

fanout이 왜 중요한지는 반대로 생각하면 분명하다. 키가 `UUID(16B)`나 긴 문자열이면
엔트리가 커지고 fanout이 떨어지며 트리가 높아진다. **인덱스 키를 작게 유지하라**는
조언은 여기서 나온다.

## B-Tree의 두 가지 한계

### 1. 내부 노드가 value를 들고 있어 fanout을 낭비한다

B-Tree는 모든 노드에 `key + value`를 저장한다. 그런데 **내부 노드의 value는 탐색에
전혀 쓰이지 않는다.** 내부 노드가 하는 일은 "어느 자식으로 내려갈지" 결정하는 것뿐이고,
그 판단에 필요한 것은 키뿐이다. value는 순수한 공간 낭비이며, 그 공간만큼 자식 수가
줄어 트리가 높아진다.

value가 6바이트 TID라면 손해는 크지 않다. 그러나 value가 **행 전체**라면(클러스터드
인덱스), 내부 노드 하나에 겨우 몇 개의 키만 들어가면서 fanout이 붕괴한다.

### 2. 범위 쿼리가 느리다

```sql
SELECT * FROM t WHERE id BETWEEN 4 AND 9;
```

B-Tree에서 이 쿼리를 처리하려면 **중위 순회(in-order traversal)** 를 해야 한다.
값이 트리 전체에 흩어져 있기 때문이다. 위 11개짜리 트리를 보자.

- `4`는 루트에 있다
- `5`는 루트의 두 번째 서브트리 → `6:800`의 왼쪽 리프
- `6`은 내부 노드에 있다
- `7`은 다시 리프
- `8`은 루트에 있다
- `9`는 오른쪽 서브트리의 리프

즉 **리프와 내부 노드를 오르내리며 트리를 헤집고 다녀야 하고**, 접근 패턴이 랜덤이다.
읽기 순서를 미리 알 수 없으니 스토리지의 prefetch/readahead도 활용할 수 없다.
정렬된 결과가 필요한 `ORDER BY`, `LIMIT`, 페이징도 같은 문제를 겪는다.

> 실무 쿼리의 상당수는 점 조회(point lookup)가 아니라 범위 조회다.
> `created_at > ?`, `status = ? ORDER BY id LIMIT 20`, `BETWEEN` 같은 것들 말이다.

## B+Tree: 두 문제를 한 번에 해결하다

B+Tree는 B-Tree에 두 가지 변경을 가한다.

1. **value는 리프 노드에만 저장한다.** 내부 노드에는 키(정확히는 자식을 가르는
   구분자, separator key)만 둔다.
2. **리프 노드들을 링크드 리스트로 연결한다.** (InnoDB와 PostgreSQL은 양방향)

```text
                        [ 5 | 9 ]                        ← Root (구분자 키만)
                     /      |      \
             [ 3 ]      [ 7 ]      [ 11 ]                ← Internal (구분자 키만)
            /    \      /   \      /    \
  Leaf:  [1:701 2:702] [3:703 4:704] [5:705 6:800] ...   ← Leaf (key+value)
            ↕            ↕             ↕
         ←──────────── 양방향 링크 ────────────→
```

여기서 주의할 점 하나. **내부 노드의 키는 리프에 다시 등장한다.** 내부 노드의 `5`는
데이터가 아니라 "5 미만은 왼쪽, 5 이상은 오른쪽"이라는 이정표이고, 실제 `5:705`는
리프에 있다. 그래서 B+Tree는 키를 약간 중복 저장하지만, 그 대가로 얻는 것이 훨씬 크다.

### 효과 1: fanout이 커지고 트리가 낮아진다

내부 노드에서 value가 사라지면 같은 페이지에 더 많은 구분자를 담을 수 있다.
특히 **모든 데이터가 리프에만 있으므로 내부 노드 전체의 크기가 작아진다.**

10억 행 인덱스에서 내부 노드 전체가 차지하는 크기를 보자. fanout이 400이면
리프를 제외한 상위 레벨 전체는 리프의 약 `1/399`, 즉 **전체 인덱스의 0.25% 수준**이다.
2.5만 페이지(200MB) 인덱스라면 상위 레벨은 500KB에 불과하다.

> 이것이 결정적이다. **B+Tree의 내부 노드는 통째로 메모리에 상주시킬 수 있다.**
> 그러면 디스크 IO는 리프 접근 1회로 줄어든다.

### 효과 2: 범위 쿼리가 순차 접근이 된다

```sql
SELECT * FROM t WHERE id BETWEEN 4 AND 9;
```

1. 루트 → 내부 → 리프로 내려가 **시작점 `4`를 한 번만 찾는다** (높이만큼의 IO)
2. 리프의 링크를 따라 `5, 6, 7, 8, 9`를 **옆으로 읽어 나간다**
3. `9`를 넘어서면 멈춘다

트리를 다시 탐색하지 않는다. 리프 페이지들은 대체로 디스크상에서도 가깝게 배치되어
있어 순차 읽기와 readahead의 이점을 그대로 받는다.

| | B-Tree | B+Tree |
|---|--------|--------|
| 시작점 찾기 | 높이만큼 IO | 높이만큼 IO |
| 이후 N개 읽기 | 매번 트리 탐색 (랜덤) | 리프 링크 따라가기 (순차) |
| readahead | 활용 불가 | 활용 가능 |

`ORDER BY id`, `LIMIT/OFFSET` 페이징, `MIN()`/`MAX()`, 커서 기반 페이징이 모두 같은
이유로 빨라진다. **리프 레벨 자체가 정렬된 연결 리스트**이기 때문이다.

### 효과 3: 리프 레벨만 훑으면 전체 스캔이 된다

인덱스만으로 답할 수 있는 쿼리(covering index / index-only scan)에서는
힙에 가지 않고 리프 체인만 순회하면 된다. `COUNT(*)`나 집계에도 유리하다.

## 실제 DBMS는 어떻게 구현하는가

### 용어에 대한 주의

MySQL과 PostgreSQL 문서 모두 인덱스 타입을 **"B-tree"** 라고 부르지만,
실제 구현은 거의 예외 없이 **B+Tree** 다. PostgreSQL의 `nbtree`는 정확히는
동시성을 위해 각 레벨에 오른쪽 형제 포인터를 둔 **Lehman-Yao B-link tree** 변형이다.
문서의 "B-tree"를 문자 그대로의 B-Tree로 읽지 않는 편이 좋다.

### MySQL InnoDB: 클러스터드 인덱스

InnoDB의 테이블은 **그 자체가 Primary Key로 정렬된 B+Tree**다
(Index Organized Table). 별도의 힙이 없다.

```text
Primary Key(클러스터드) B+Tree
   Leaf = [PK | 나머지 컬럼 전부]   ← 리프가 곧 테이블 데이터

Secondary Index B+Tree
   Leaf = [인덱스 키 | PK 값]      ← 힙 포인터가 아니라 PK를 저장
```

여기서 두 가지 실무 함의가 나온다.

- **세컨더리 인덱스 조회는 기본적으로 두 번의 트리 탐색이다.** 세컨더리 인덱스에서
  PK를 얻고, 그 PK로 클러스터드 인덱스를 다시 탐색한다(bookmark lookup).
  필요한 컬럼이 세컨더리 인덱스 안에 모두 있으면(covering index) 두 번째 탐색이
  생략된다.
- **PK가 크면 모든 세컨더리 인덱스가 함께 비대해진다.** PK가 `UUID(16B, CHAR(36)이면
  36B)`이면 그 크기가 모든 세컨더리 인덱스의 모든 리프 엔트리에 복제된다.
  인덱스가 5개면 낭비도 5배다.

### PostgreSQL: 힙 + 세컨더리 인덱스

PostgreSQL에는 클러스터드 인덱스가 없다. 데이터는 힙에 있고, **PK를 포함한 모든
인덱스가 동등하게 세컨더리 인덱스**이며 리프에 TID(6B)를 저장한다.

- PK 크기가 다른 인덱스에 전파되지 않는다
- 대신 인덱스 조회는 **항상 힙 접근이 필요**하다 (index-only scan 제외)
- `index-only scan`은 **visibility map**에서 해당 힙 페이지가 all-visible로 표시된
  경우에만 힙 접근을 생략할 수 있다. `VACUUM`이 제때 돌지 않으면 index-only scan을
  기대해도 힙을 읽게 된다
- 행이 갱신되면 새 버전(tuple)이 생기고 TID가 바뀌므로 인덱스도 갱신되어야 한다.
  갱신된 컬럼이 인덱싱되어 있지 않고 같은 페이지에 공간이 있으면 **HOT update**로
  인덱스 갱신을 피한다

| 항목 | MySQL (InnoDB) | PostgreSQL |
|------|----------------|------------|
| 테이블 저장 | PK 기준 클러스터드 B+Tree | 힙 (정렬 없음) |
| 세컨더리 인덱스 value | PK 값 | TID (페이지, 오프셋) |
| PK 크기의 영향 | 모든 세컨더리 인덱스에 전파 | 영향 없음 |
| PK 순서 범위 스캔 | 리프가 곧 데이터, 매우 빠름 | 힙 랜덤 접근 발생 |
| 인덱스만으로 조회 | covering index | index-only scan + visibility map |
| 페이지 크기 | 16KB | 8KB |
| 언더플로 시 병합 | `MERGE_THRESHOLD`(기본 50%)로 병합 | 병합하지 않음, 빈 페이지만 회수 |

## B+Tree의 대가

B+Tree는 만능이 아니다. 읽기에 최적화된 구조인 만큼 쓰기에서 값을 치른다.

**페이지 분할(page split)과 단편화.** 삽입 위치가 랜덤하면 가득 찬 리프가 계속
쪼개진다. 분할된 페이지는 각각 절반만 차서 인덱스 크기가 부풀고(bloat), 논리적
순서와 물리적 순서가 어긋나 범위 스캔의 순차성이 무너진다.

**쓰기 증폭(write amplification).** 8바이트 키 하나를 추가해도 8KB 페이지 전체가
더티가 되어 다시 쓰인다. 여기에 WAL 기록까지 더해진다.

**인덱스 개수만큼 곱해지는 쓰기 비용.** `INSERT` 한 번은 테이블 쓰기 한 번이 아니라
`1 + 인덱스 개수`만큼의 B+Tree 갱신이다. 쓰지 않는 인덱스는 순수한 손해다.

이 때문에 쓰기가 압도적으로 많은 워크로드에서는 **LSM Tree**(RocksDB, Cassandra,
ScyllaDB 등)를 쓴다. LSM은 쓰기를 메모리에 모아 순차적으로 flush해 랜덤 쓰기를
없애는 대신, 읽기 시 여러 SSTable을 확인해야 하고 컴팩션 비용을 부담한다.
**B+Tree는 읽기 최적화, LSM Tree는 쓰기 최적화**라는 트레이드오프다.

## 실무로 옮기면

**랜덤 PK를 피하라.** `UUIDv4`를 PK로 쓰면 삽입 위치가 매번 무작위여서 클러스터드
인덱스 전역에 페이지 분할이 발생하고, 버퍼 풀 적중률도 떨어진다. 시간 순으로 증가하는
`AUTO_INCREMENT`/`BIGSERIAL`이나 `UUIDv7`/`ULID`를 쓰면 삽입이 항상 오른쪽 끝에서
일어나 분할이 최소화된다. InnoDB에서는 PK 크기가 모든 세컨더리 인덱스에 전파되므로
효과가 배가된다.

**인덱스 키를 작게 유지하라.** 키가 작을수록 fanout이 크고 트리가 낮다. 긴 문자열
컬럼은 접두사 인덱스나 해시 컬럼을 고려한다.

**복합 인덱스의 컬럼 순서가 곧 정렬 순서다.** B+Tree 리프는 인덱스 정의 순서대로
정렬되어 있으므로, `(a, b)` 인덱스는 `a` 또는 `a, b` 조건에는 쓰이지만 `b`
단독 조건에는 쓰이지 않는다.

**범위 조건 컬럼은 뒤로 보내라.** 리프 체인을 순차적으로 훑는 구조 때문에, 등치
조건을 앞에, 범위 조건을 뒤에 두어야 스캔 구간이 좁아진다.

**커버링 인덱스를 활용하라.** InnoDB의 bookmark lookup이나 PostgreSQL의 힙 접근을
없앨 수 있다. PostgreSQL은 `INCLUDE` 절로 키가 아닌 컬럼을 리프에만 얹을 수 있다.

## Summary

| 항목 | B-Tree | B+Tree |
|------|--------|--------|
| 내부 노드 저장 내용 | key + value | **key(구분자)만** |
| value 위치 | 모든 노드 | **리프 노드에만** |
| 키 중복 | 없음 | 구분자 키가 리프에 다시 등장 |
| 리프 연결 | 없음 | **양방향 링크드 리스트** |
| fanout | 상대적으로 작음 | **큼 (내부 노드가 작아서)** |
| 트리 높이 | 상대적으로 높음 | **낮음** |
| 점 조회 | 운이 좋으면 내부 노드에서 조기 종료 | 항상 리프까지 내려감 (예측 가능) |
| 범위 쿼리 / ORDER BY | 느림 (트리 순회, 랜덤 IO) | **빠름 (리프 순차 스캔)** |
| 내부 노드 캐싱 | 불리 (크기가 큼) | **유리 (전체 인덱스의 1% 미만)** |
| DBMS 채택 | 거의 없음 | **대부분의 RDBMS** |

핵심을 한 줄로 줄이면 이렇다.

> **B+Tree는 "탐색에 필요한 것(키)"과 "결과에 필요한 것(값)"을 분리해서,
> 상위 레벨은 메모리에 올리고 리프 레벨은 정렬된 연결 리스트로 만든 구조다.**
